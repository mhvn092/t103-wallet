# T-103: Crypto Exchange Wallet & Double-Entry Ledger — Design Document

**Version:** v1.3 (Post-Audit Hardened) | **Stack:** NestJS 12, TypeScript, PostgreSQL 18, Drizzle ORM (`pg`), RabbitMQ (bonus), No Redis  
*Empirical behaviors captured from `hamtapay/t103-simulator:1.0` (`default` & `hostile`) are logged with evidence in [`docs/provider-notes.md`](./provider-notes.md).*

---

## 1. Service & Module Boundaries

**NestJS Modular Monolith** over Microservices: keeps Wallet, Ledger, Limits, and Outbox inside single-DB ACID transactions—eliminating distributed `2PC`/Saga drift—while scaling horizontally via stateless replicas (like Shopify's BFCM Modular Monolith), with PostgreSQL as sole source of truth, inbound/outbound `X-Request-Id` correlation propagation, and a global `ExceptionFilter` enforcing `{"code", "message"}` on all errors:

- **`WalletModule` & `LedgerModule`**: Lazy user sub-accounts (`AVAILABLE`, `LOCKED`, `RECEIVABLE`), DB-materialized double-entry engine (`LedgerService.postTransaction()` atomically writes `outbox_events` in the same TX whenever any `USER` balance changes), `GET /wallets/:userId` (`200` with `"0"` balances for unseen users, never `404`), and keyset-paginated `GET /wallets/:userId/ledger` (defaults to `AVAILABLE`; `?accountType=ALL` optional).
- **`IdempotencyModule`**: User-scoped `PK(route:userId, key)` + canonical key-sorted JSON SHA-256 `request_hash` (`422 IDEMPOTENCY_KEY_REUSED` on mismatch evaluated before domain business rules). On DB-only POSTs (`/withdrawals`, `/transfers`, `/internal/adjustments`, `/internal/receivables/settle`), **Statement #1** of the `READ COMMITTED` TX is `INSERT INTO idempotency_keys (..., 'IN_PROGRESS') ON CONFLICT (scope, key) DO NOTHING`: PostgreSQL's PK index blocks concurrent identical retries until the winner updates `COMPLETED` (`201`/`200`), so waiters read and replay cached responses *before* touching `accounts` (never falsely returning `422 INSUFFICIENT_FUNDS`), while `4xx` rollbacks leave retries uncached. External-PSP `POST /deposits` commits a 60s `IN_PROGRESS` lease (`locked_until`, fenced by `lease_version` CAS) before calling PSP (`409 IDEMPOTENCY_IN_PROGRESS` while active or on stale overwrite). `RetentionWorker` purges expired `idempotency_keys` (`expires_at`), 7d `PUBLISHED` `outbox_events`, and 30d `processed_events` in bounded batches.
- **`DepositModule`**: Initiates PSP payments (`POST /deposits`), treats unsigned callbacks as wake-up hints only, fences unsettled updates with `(status, version)` CAS, checks `orderId` (deduplicated discrepancy logging + poll halt) + non-10x IRR remainders (`hasIrrRemainder`), preserves a post-expiry `DEPOSIT_EXPIRY_GRACE_MS` poll window, sizes worker leases above `PROVIDER_HTTP_TIMEOUT_MS` (`computeSafeLeaseMs`), and runs `DepositPoller` for dropped callbacks, crashes, and expiry recovery.
- **`WithdrawalModule`**: Enforces idempotency replay before DTO bounds (`MAX_AMOUNT_MINOR = 10^15`), runtime `system_controls` pause flags (`503 SERVICE_PAUSED`), destination/minimum/restrictions/limits, holds funds (`AVAILABLE → LOCKED`), supports idempotent pre-dispatch cancel (`PENDING_DISPATCH`), dispatches payouts via `SKIP LOCKED` + `version` fencing + timeout-scaled leases + jittered `503` retry backoff, escalates SLA-breaching `DISPATCHING` and `PROCESSING` rows to `MANUAL_REVIEW` (while safely CAS re-dispatching unaccepted `provider_ref_id IS NULL` `MANUAL_REVIEW` rows on `404`), verifies raw-body HMAC-SHA256 webhooks (+ deduplicated payload mismatch auditing), offsets `USER:RECEIVABLE` first on `WD_RETURN`, and shields `RETURNED`/`CANCELLED_BY_USER` rows from false `WD_LATE_SUCCESS`.
- **`AdjustmentModule` & Health**: `POST /internal/adjustments`, `POST /internal/receivables/settle`, `POST /internal/controls/withdrawals-pause`, `GET /internal/metrics` (backed by `DriftAuditWorker` + single-flight `DRIFT_AUDIT_INTERVAL_MS` cached drift gauge), and `POST /reconciliation/run` are guarded by `InternalOpsGuard` (unconditionally requiring timing-safe `INTERNAL_API_KEY` when `APP_ENV=production`, plus optional `INTERNAL_ALLOWED_IPS` honoring `TRUST_PROXY`). Kubernetes liveness (`/health`, `/health/liveness`) and bounded-timeout Postgres readiness (`/ready`, `/health/readiness`, failing `503` immediately on `SIGTERM` drain and enforcing DB `statement_timeout`) probes follow env-validated configuration (`DATABASE_URI`, `MIGRATION_DATABASE_URI`, `RABBITMQ_URI`, `SWAGGER_ENABLED`); startup `runMigrations()` serializes across replicas via `pg_advisory_lock(840103)` (requiring a direct/session-mode `MIGRATION_DATABASE_URI`) and provisions the least-privilege `t103_app` runtime DML role in Compose.
- **`ProvidersModule`**: Isolated HTTP adapters (`PspClient`, `PayoutClient`) propagating `X-Request-Id`, handling timeouts, raw-body lowercase-hex HMAC verification, `IRT × 10 ↔ IRR` conversion on **both** PSP and Payout, and Persian/dirty-CSV normalization.
- **Bonus Modules**: `TransferModule` (`POST /transfers`, rejects `fromUserId === toUserId` with `400`), `ReconciliationModule` (`POST /reconciliation/run` read-only CSV diff using index-friendly `RECONCILIATION_TZ` half-open `[start, end)` timestamp bounds, consuming matched local rows cleanly across duplicate refs, handling negative CSV amounts safely, normalizing Persian digits/`000`-padded refs), and `OutboxModule` (RabbitMQ `ConfirmChannel` + `lease_until` + non-blocking auto-reconnect so Broker outages never block boot/writes + `processed_events` dedup).

**Multi-Instance Coordination:** Stateless instances share no in-memory locks; workers (`DepositPoller`, `WithdrawalDispatcher`, `WithdrawalPoller`, `OutboxRelay`, `RetentionWorker`) claim work with `SELECT ... FOR UPDATE SKIP LOCKED`, `lease_until`, and monotonic `version`/`lease_version` fencing tokens.

## 2. Data Model (Tables, Keys, Indexes & Constraints)

All entity PKs use time-ordered **`UUIDv7`** (`uuid`). Monetary columns use **`NUMERIC(38,0)` minor units** (`1 IRT = 1 Toman`, `1 USDT = 1,000,000 micro-USDT`), mapping 1:1 to TypeScript `bigint` with zero floats.

| Table | Key Columns & Types | Constraints & Critical Indexes |
| --- | --- | --- |
| `accounts` | `id UUIDv7 PK`, `owner_type` (`USER\|SYSTEM`), `owner_id`, `currency` (`IRT\|USDT`), `account_type` (`AVAILABLE\|LOCKED\|RECEIVABLE\|CLEARING\|ADJUSTMENT\|REVENUE`), `normal_side` (`DEBIT\|CREDIT`), `balance NUMERIC(38,0)` (`NULL` on `SYSTEM`) | `UNIQUE(owner_type, owner_id, currency, account_type) INCLUDE (id)` (mutable `balance` omitted to preserve HOT updates); `accounts_type_normal_side_chk`; `CHECK ((owner_type = 'SYSTEM' AND balance IS NULL) OR (owner_type = 'USER' AND balance >= 0))`; `BEFORE UPDATE OF balance` forbids direct SQL edits; `trg_accounts_immutable_meta` rejects non-zero `USER` inserts and immutable column/`normal_side` changes |
| `ledger_transactions` | `id UUIDv7 PK`, `type`, `reference_type`, `reference_id`, `description`, `metadata JSONB`, `created_at` | `UNIQUE(reference_type, reference_id, type) INCLUDE (id)`; append-only trigger (`UPDATE`/`DELETE`/`TRUNCATE`); `DEFERRABLE INITIALLY DEFERRED` commit trigger enforcing `COUNT(*) >= 2` and per-currency `SUM(DEBIT) = SUM(CREDIT)` |
| `ledger_items` | `id BIGINT GENERATED ALWAYS AS IDENTITY PK`, `transaction_id FK`, `account_id FK`, `user_id`, `account_type`, `currency` (`IRT\|USDT`), `direction` (`DEBIT\|CREDIT`), `amount NUMERIC(38,0)`, `balance_after` (`NULL` on `SYSTEM`) | Append-only trigger (`UPDATE`/`DELETE`/`TRUNCATE`); `BEFORE INSERT` trigger verifies parent TX belongs to `pg_current_xact_id()`, updates `USER` `accounts.balance` via `normal_side`, and sets `balance_after`; `CHECK (amount > 0)`; covering `ledger_items_tx_idx` + covering partial index `(user_id, account_type, id DESC) INCLUDE (transaction_id, currency, direction, amount, balance_after) WHERE user_id IS NOT NULL` |
| `user_daily_limits` | `user_id TEXT`, `limit_date DATE`, `used_irt_amount NUMERIC(38,0)` | `PK(user_id, limit_date)`, `CHECK (used_irt_amount >= 0)` |

| `idempotency_keys` | `scope TEXT`, `key TEXT`, `request_hash`, `status`, `response_status`, `response_body JSONB`, `locked_until`, `lease_version BIGINT`, `expires_at` | `PK(scope, key)`; index on `expires_at`; purged in batches by `RetentionWorker` |

| `adjustments` | `id UUIDv7 PK`, `user_id`, `currency`, `amount`, `reason`, `operator_id`, `created_at` | Audit record referenced by `OPS_ADJ` ledger transaction |

### Double-Entry Posting Matrix (`CREDIT = +` on `CREDIT`-normal `AVAILABLE`/`LOCKED`/`FEE_REVENUE`; `DEBIT = +` on `DEBIT`-normal `RECEIVABLE`/clearing)

| Event (`type`) | Debit Account(s) | Credit Account(s) |
| --- | --- | --- |
| Deposit Succeeded (`DEPOSIT`) | `SYSTEM:PSP_CLEARING` (`verified`, `+`) | `USER:{id}:IRT:AVAILABLE` (`verified`, `+`) |
| Ops Credit (`OPS_ADJ`) | `SYSTEM:OPS_ADJUSTMENT` (`+`) | `USER:{id}:{ccy}:AVAILABLE` (`+`) |
| Withdrawal Hold (`WD_HOLD`) | `USER:{id}:{ccy}:AVAILABLE` (`amount + fee`, `-`) | `USER:{id}:{ccy}:LOCKED` (`amount + fee`, `+`) |
| Withdrawal Succeeded (`WD_SETTLE`) | `USER:{id}:{ccy}:LOCKED` (`amount + fee`, `-`) | `SYSTEM:PAYOUT_CLEARING` (`amount`), `SYSTEM:FEE_REVENUE` (`fee` if > 0) |
| Withdrawal Failed / Cancelled (`WD_RELEASE`) | `USER:{id}:{ccy}:LOCKED` (`amount + fee`, `-`) | `USER:{id}:{ccy}:AVAILABLE` (`amount + fee`, `+`) |
| Bank Return (`WD_RETURN`) | `SYSTEM:PAYOUT_CLEARING` (`amount`), `SYSTEM:FEE_REVENUE` (`fee` if > 0) | `USER:{id}:{ccy}:RECEIVABLE` (`min(receivable, totalRefund)`, `-` debt), remainder to `USER:{id}:{ccy}:AVAILABLE` (`+`) |
| Late-Success Conflict *(Ambiguity #1)* (`WD_LATE_SUCCESS`) | `USER:AVAILABLE` (`clawback`, `-`), `USER:RECEIVABLE` (`shortfall`, `+ >= 0`) | `SYSTEM:PAYOUT_CLEARING` (`amount`), `SYSTEM:FEE_REVENUE` (`fee` if > 0) |
| Receivable Settlement (`RECEIVABLE_SETTLE`) | `USER:{id}:{ccy}:AVAILABLE` (`-`) | `USER:{id}:{ccy}:RECEIVABLE` (`-` debt; unfreezes when zero) |
| Internal Transfer *(bonus)* (`TRANSFER`) | `USER:{from}:{ccy}:AVAILABLE` (`-`) | `USER:{to}:{ccy}:AVAILABLE` (`+`) |

**Canonical Lock Order:** Lazy `INSERT ... ON CONFLICT DO NOTHING` upserts run deterministically sorted by `(owner_type, owner_id, currency, account_type) ASC` (or autocommit pre-ensure) *before* acquiring `SELECT ... FOR UPDATE` locks in strict order: `idempotency_keys (scope, key)` → `user_daily_limits (user_id, limit_date)` → `user_restrictions (user_id)` → **`USER` `accounts` sorted by `id ASC`** (deadlock-free even on brand-new users). `SYSTEM` accounts keep `balance IS NULL` and are never locked or updated.

## 3. State Machines (Deposits & Withdrawals)

### Deposit State Machine
`INITIATED` → `AWAITING_PAYMENT` → `VERIFYING` → `SUCCEEDED` | `FAILED` *(with post-expiry grace recovery)*

- **Initiation:** `POST /deposits` claims user-scoped `idempotency_keys` (`POST:/deposits:<userId>`, `IN_PROGRESS`, `locked_until = now + 60s`, fenced by `lease_version`), inserts `INITIATED`, calls `POST /psp/payments` (`amount_irt * 10` IRR), commits `AWAITING_PAYMENT` + `psp_token` + `expires_at` (`+30m`) fenced by `lease_version` *before* returning `201`. Orphaned `INITIATED` rows (`psp_token IS NULL`) past 65s expire safely to `FAILED`.
- **Verification & Recovery:** Unsigned PSP callbacks (`{token, orderId, status: "OK"|"NOK"}`) act as wake-up hints only (never mark `FAILED`). Callers query `GET /psp/payments/{token}` before `POST /psp/verify`, verify `orderId` matching (logging deduplicated `ORDER_ID_MISMATCH` and halting polling with `next_poll_at = NULL` without crediting on mismatch), fence unsettled transitions via `(status, version)` CAS, and preserve a post-expiry `DEPOSIT_EXPIRY_GRACE_MS` polling schedule so late `PAID` confirmations recover `FAILED → SUCCEEDED`. Both `code: 100 ("OK")` and `code: 101 ("ALREADY_VERIFIED")` settle exact `verified_amount` (`÷ 10n` IRT) and flag `AMOUNT_MISMATCH` on differing totals or non-10x IRR remainders (`hasIrrRemainder`). `/reconciliation/run` normalizes `شماره پیگیری` (`000`-strip/trim), Persian digits, duplicate rows, negative deposit safety, and `واریز درگاه` lines using index-friendly `RECONCILIATION_TZ` ranges while consuming matched local deposits once.

### Withdrawal State Machine
`PENDING_DISPATCH` → `DISPATCHING` → `PROCESSING` → `SUCCEEDED` | `FAILED` *(plus `MANUAL_REVIEW` for unresolved states)*

- **Validation, TX1 & Cancellation *(Ambiguity #3)*:** User-scoped `Idempotency-Key` claim/replay runs *first* (invalid reuse yields `422 IDEMPOTENCY_KEY_REUSED`), followed inside the TX by `MAX_AMOUNT_MINOR` bounds, `400 INVALID_DESTINATION` (ISO-13616 Mod-97 IBAN / Base58Check TRC20), `422 BELOW_MINIMUM` (`100,000` IRT / `10` USDT), runtime `system_controls` currency pause (`503 SERVICE_PAUSED`), canonical locks, `outbound_frozen` (`403`), `DAILY_LIMIT_EXCEEDED` (`200M` IRT eq.), and `INSUFFICIENT_FUNDS`; executes `WD_HOLD`, increments `user_daily_limits`, and inserts `PENDING_DISPATCH` with pre-generated `provider_request_id` (`version = 1`). Cancellation is idempotent (`200 OK` if already `CANCELLED_BY_USER`) and allowed strictly before dispatch (`409` once `DISPATCHING`+).
- **Dispatch & TOCTOU Fencing:** `WithdrawalDispatcher` claims `PENDING_DISPATCH` via `SKIP LOCKED`, increments `version`, sets `lease_until = now() + computeSafeLeaseMs(45s, timeoutMs, 2, 15s)` (strictly exceeding `PROVIDER_HTTP_TIMEOUT_MS`), commits `DISPATCHING`, and calls `POST /payout/transfers`. Definitely rejected `4xx` responses release funds; `5xx`/timeouts compute short jittered exponential backoff (`computeJitteredBackoffMs`, avoiding 45s stalls), query `GET /payout/transfers/{provider_request_id}` on recovery, re-POST with identical `provider_request_id` on `404`, and escalate to `MANUAL_REVIEW` from either `DISPATCHING` or `PROCESSING` once `age >= WD_MANUAL_REVIEW_SLA_MS`. When `pollProcessingBatch` sees `404` on an unaccepted `MANUAL_REVIEW` row (`provider_ref_id IS NULL`), it atomically CAS-reclaims `status = 'DISPATCHING'` with a fresh dispatch lease and `version + 1` before calling `createTransfer`, avoiding concurrent duplicate `POST`s while never blindly re-POSTing previously accepted (`provider_ref_id IS NOT NULL`) rows.
- **Webhooks, Returns & Late-Success *(Ambiguity #1)*:** Payout webhooks validate raw-body HMAC-SHA256 hex signatures (`401` on invalid), check optional payload `amount`/`currency` against stored withdrawal values (`PAYOUT_PAYLOAD_MISMATCH`), lock `FOR UPDATE` + pre-scaffold `[AVAILABLE, IRT RECEIVABLE, USDT RECEIVABLE]` to prevent webhook TOCTOU `500`s, and allow strictly forward transitions. Duplicate/out-of-order `SUCCEEDED` webhooks after `WD_SETTLE` + `WD_RETURN` or `CANCELLED_BY_USER` are ignored safely; explicit `RETURNED`/`REVERSED` settlements post `WD_RETURN`, credit `USER:RECEIVABLE` first to retire any prior late-success debt before crediting `USER:AVAILABLE`, and automatically clear `outbound_frozen = false` once all receivables reach zero.

## 4. Key Assumptions

1. **Unit Boundary:** API amounts are strings (`IRT` integer Toman; `USDT` up to 6 decimals). **Both** PSP and Payout (`IRR`) expect Rials (`1 IRT = 10 IRR`), translated exclusively inside `ProvidersModule` (`docs/provider-notes.md`).
2. **Minimum IRT Withdrawal:** `100,000` Toman per Business Rules (env-configurable; Appendix A's `50,000` is illustrative).
3. **Daily Limit *(Ambiguity #2)*:** `200,000,000` Toman per `Asia/Tehran` (`00:00`) day across `IRT + USDT` combined (`USDT` converted via integer ceiling `(amount_minor * fx_rate_irt + 999_999n) / 1_000_000n` with snapshotted `USDT_IRT_RATE`; `FAILED`/`RETURNED`/cancelled release quota).
4. **Arithmetic & Keys:** Zero floats (`NUMERIC(38,0)` minor units in Postgres + `bigint` in TS); `UUIDv7` entity PKs + `BIGINT` identity ledger cursor; lazy user account creation.

## 5. Architecture Decision Records (ADRs)

- **ADR-01: PostgreSQL Row-Level Locking Over Redis Distributed Locks**
  - *Options:* (A) Redis Redlock/counters; (B) PostgreSQL `FOR UPDATE` + `SKIP LOCKED` + `CHECK`. *Decision:* Option B.
  - *Trade-off:* Higher hot-row contention at extreme scale (Phase 1: Postgres sub-buckets/micro-batching; Phase 2: hot-ledger offload to **TigerBeetle** using `UUIDv7` `u128` idempotency), but eliminates Redis split-brain, cache-DB drift, and negative-balance races on Redis CPU saturation.
- **ADR-02: DB-Materialized Double-Entry `accounts`/`ledger_items` with Minor-Unit `NUMERIC(38,0)` & Unupdated `SYSTEM` Accounts**
  - *Options:* (A) App-updated wallet balance columns or locked system rows; (B) Immutable `ledger_items` + `BEFORE INSERT` balance-projection trigger (`pg_trigger_depth()` guard forbidding direct SQL edits) + per-currency deferred zero-sum trigger on `ledger_transactions`, `normal_side`-typed `NUMERIC(38,0)` (`balance >= 0` everywhere), `balance IS NULL` on `SYSTEM`. *Decision:* Option B.
  - *Trade-off:* Extra hold/release rows and trigger overhead, but mathematically prevents balance-vs-ledger drift (`SUM(CREDIT) - SUM(DEBIT) == balance` for liabilities, vice versa for assets), negative balances, float error, and global clearing-row contention.
- **ADR-03: Commit-First Async Payout Dispatch with `version`-Fenced Leases & No Timeout Auto-Fail**
  - *Options:* (A) Inline Payout inside `POST /withdrawals` and auto-fail on timeout; (B) Persist hold + `provider_request_id` in TX1, dispatch async with `version` CAS (`timeout < lease`), escalate prolonged ambiguity to `MANUAL_REVIEW`. *Decision:* Option B.
  - *Trade-off:* Async payout completion and longer holds during outages, but prevents double payouts, TOCTOU zombie overwrites, and premature refunds on unknown bank outcomes.
- **ADR-04: Modular Monolith Over Microservices**
  - *Options:* (A) Split Wallet/Ledger/Withdrawal/Limits into microservices with 2PC/Sagas; (B) NestJS Modular Monolith over shared ACID PostgreSQL. *Decision:* Option B.
  - *Trade-off:* Shared DB deployment unit, but eliminates partial-failure Saga windows and scales horizontally via stateless API/worker pods (proven at extreme financial throughput by Shopify's BFCM Modular Monolith).
